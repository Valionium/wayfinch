## One theme for both apps (owner's try-out, 5 November 2026)

Each app writes only its own record of a theme the rider chose, `{app, kind: 'theme', v: 1, theme, at}`: Wayfinch `copilot:theme:v1` (You's Theme, and an import that brings settings; `src/ui/theme-choice.ts`), the bag planner `loadcheck:theme:v1` (its theme button and Apply imported settings; it still writes `loadcheck:theme` for older pages). Both read both and show the most recent, at the same moment Wayfinch's; with neither, Wayfinch's own light or dark from `copilot:settings`, else the bag planner's `loadcheck:theme`, else automatic. `themeFrom` in `src/ui/theme-choice.ts` and the page's `themeChoiceFrom` decide alike (`THEME-ONE`). Wayfinch's first screen carries only `firstTheme` (`src/ui/theme-apply.ts`: the newer of the two records, checked as both apps write them, else its own setting); `src/ui/page-return.ts`, loaded right after, applies the rule and follows the bag planner's storage events, `pageshow` and `visibilitychange` (the bag planner follows Wayfinch's the same way). A rider whose only choice is Load Check's older `loadcheck:theme` sees it once that module has loaded on the first start; the rule then writes it as Wayfinch's own record dated 1970-01-01, at a start only (after Delete co-pilot data the open page writes nothing back), so every later start paints it at once and any real choice is newer. Each app stamps a new record just after the other's when that one is dated later (a clock set wrong). Delete co-pilot data removes Wayfinch's record. A working plan's theme is no longer applied when the bag planner starts. Wayfinch's export carries the one theme.

## One chosen bike for every tool (sub-project 11, group 2)

Each app writes only its own record of the bike the rider chose, `{app, kind: 'bike-choice', v: 1, bikeId, at}`: Wayfinch `copilot:bikeChoice:v1` (`src/ui/tools/bike-choice.ts`: the Tools bike line, the tyre tool's bike box, a `?bike=<id>` address, an import that brings settings), the bag planner `loadcheck:bikeChoice:v1` (group 3: every change of the plan's bike made in the page, by any path: a pick, a setup loaded, an imported working plan, a plan-only "My bike", Undo; only the follow writes none; through `store.set`, so it is stamped for C-DELETE). `bikeId` matches `/^[a-zA-Z0-9_-]{1,100}$/`, or is null for No bike. Both apps read both and use the newer, at the same moment Wayfinch's (as `THEME-ONE`); a wrong app, kind, version, id or date is no record. A new record is stamped one millisecond after the other app's when that is dated later (a clock set wrong, `TB-CHOICE-CLOCK`). Wayfinch never writes a `loadcheck:*` key (`TB-NO-LC-WRITE`). The choice only counts while that bike is in the bag planner's saved list; otherwise, as in the tyre tool (PR 51), the bike in use stands (`toolBike` in `src/tools/tyre/choice.ts`: the plan's, else the one saved last, else the current one, else the last in the list), and a plan bike that is not saved is never offered. No bike is a choice only when the rider picked it, never because no bike existed. A choice made elsewhere while the tyre tool is open follows silently if the rider has not picked or typed there, otherwise it offers a Switch (`TB-ELSEWHERE`). The export carries the choice as `settings.toolBike` (a bike id, or null: No bike and no choice read the same there); an import writes the record. A choice never touches `copilot:settings`, so it cannot bump the stamp under an open You form. The Tools screen's bag card is in the first screen; its bike line and tyre card are a chunk of their own. In the bag planner the chosen bike is the plan's bike (decision 4: its saved-bike picker is its bike line). A newer Wayfinch record naming a saved bike that is not the plan's moves the plan to it when the page opens (`followBikeChoice()`: at a plain start-up, after the draft is restored and the bikes are loaded, and on `pageshow` from the back/forward cache; never on a storage event, so the plan never changes under the rider's fingers; never on a visit through a Bike details link, which is a side trip; never while Bike details is open, a save is under way or the draft is frozen by another tab). A Wayfinch record is followed at most once, and one naming the plan's own bike counts as seen too: the stamp it last acted on is kept in the page's own `loadcheck:bikeFollowed:v1` (through `store.set`, stamped), so a change of the plan's bike that writes no record (an older bag-planner tab) is never undone by an old choice. A plan-only bike (in no saved list) is never replaced by a follow, since Undo lives in memory only. A newer Wayfinch record of No bike ("Without a bike" in Tools, owner's ruling of 7 November 2026) moves the plan to no bike, the standard bike, in the same way and with the same guards, with the line "Now planning without a saved bike · Undo", never silently; with no plan bike already it is only seen; Tools' bag card then draws the grey standard bike and says "No bike chosen. The Bag planner uses a standard bike." (`TB-PAGE-NO-BIKE`). The move comes with the line "Now planning for <name>, chosen in Tools · Undo"; that Undo is the bike-swap Undo (`BIKE_SWAPS`, `undoBikeSwap`), and it writes the page's record for the bike it brings back (`TB-PAGE-FOLLOWS`, `TB-PAGE-UNDO`, `qa/bike-choice.cjs`). Following writes no record.

## Contract for C-DELETE (sub-project 6): Also delete bag planner data

You stores `copilot:delete-request:v1` = {app, kind, v: 1, id, createdAt} and opens `/tools/bags/#copilot-delete=<id>`. The bag planner's half is `applyDeleteRequest()` (sub-project 6, group 2), the first thing its start-up does, before the draft is restored. It deletes only the bag-planner data that was saved **before `createdAt`**, and never anything made or saved later: a rider who taps Also delete bag planner data, then builds a new plan days before the bag planner first applies the request, keeps the new plan. Spec section 7.1, Contract 3, says the request is applied "before it restores its draft" and names the id; it does not name this limit, so this note adds it. A request is applied at most once, and never from the fragment alone; the fragment is removed in every case. How "before" is known: the draft by its `updatedAt`, setups and reports by their own times, everything else by `loadcheck:saved-at:v1`, which the page's `store.set` stamps when a value changes (bikes and setups one by one). A setup has one stamp whichever of the two setup lists holds it (`loadcheck:setups` or `loadcheck:setups-more:v1`; both lists are judged by the stamps kept under `loadcheck:setups`), and it changes only when what the page reads for that setup changes, so a move between the lists, or its marks put back after an older page dropped them, is not a change (`stampSetups`; review of PR 80, m-1). What only the page live before this one (main's, also after a rollback to it) can do, since its code is fixed: its own setup write keeps stamps only for the 20 setups it holds, so a setup in the second list then has only its own times and goes at a later apply unless those are later, even if it changed after the request; it drops the marks of the setups it writes, and its ledger counts those setups as changed then, so they stay at a request made before that write and applied after it; and when it applies a request itself, it keeps or removes `loadcheck:setups-more:v1` and `loadcheck:setup-marks:v1` whole, by their own stamps, which this page sets to the newest stamp of the setups in each: the second list stays whole (setups saved before the request with it) only when one of its setups was saved after the request, and goes whole otherwise. The tagged site's page and the frozen copy at / stamp nothing and apply no request (known risk (2) below). An older page stamps nothing: where its value carries its own time (a draft's `updatedAt`, a setup's `updated` or a later day in its `saved`, a report's `at`, a bike's `geometry.at`), that time decides; a value with no time at all goes, the careful side for a rider who asked for deletion. A time later than now (the clock set back since) counts as after the request. A save whose stamp could not be written (storage full: the value is written first, the ledger after) has no stamp and goes at a later apply, though it was saved after the request. A value stamped while the device clock was ahead of the request's time is kept, so a delete can then delete too little. The deleting tab writes `loadcheck:delete-applying` before its first removal; every tab checks it and `loadcheck:delete-applied` before each save and when it shows again (back/forward cache), and then drops all it holds and reloads. Any new `loadcheck:*` key written outside `store.set` must call `stampKey`, or C-DELETE treats it as old. Tests: `qa/contracts.cjs`, `tests/e2e/app-contracts.spec.ts`.

## Known risks: old Load Check tabs after the launch (sub-project 6, group 4)

A tab of the old page (the tagged site's or the frozen `/` copy) left open across the launch is frozen code: it can't be fixed, only documented. Its draft is safe (it compares versions before every write, M9). Five risks are pinned as tests of today's real behaviour, named "known risk, not a guarantee" in `tests/e2e/launch.spec.ts` (`SW-OLD-TAB-WRITES`, `BK-PAINT-OLD-PAGE`, `BK-DETAILS-OLD-PAGE`): (1) its bike writes replace the bike list wholesale, so a bike or Look the bag planner saved since is lost when the old tab saves a bike, because both pages are at bike format 2 and the format guard never fires (writing format 3 would stop it but would lock bike editing for good if the frozen copy were ever served at `/` again: the owner's call, review I1); (2) a setup or bike it saves in the moment between a delete request and its apply has no stamp and goes with the rest (M1); (3) after Also delete bag planner data it still holds the deleted setups and bikes in memory and writes them back with its next save (M2); (4) whatever bike it writes loses its look extras (`look.paint`: pattern, fork, rims; the owner's wish of 5 November 2026), since its own reader does not know them: a bike it re-saves to the bike list, and the plan's bike in a draft or a setup it saves, the fork's own two colours included; the colour, handlebar and e-bike stay, so the bike then draws in its first colour, as before the extras. A bag-planner tab opened before the fork's own colours (6 November 2026) knows the presets but not the two colours: whatever it re-saves keeps `pair`, the nearest preset, and drops `colours`, so that fork then draws in its preset pair (not pinned: that page is not served anywhere after the launch). That preset is only the nearest by colour distance and can look far from the rider's pair (Red to Yellow stores Olive to sand; review of PR 50, M3, accepted): only such a tab, and a colour that breaks, ever draw it. The format stays 2 for the reason in (1); pinned in `tests/e2e/launch.spec.ts` (`BK-PAINT-OLD-PAGE`). (5) Whatever bike it re-saves loses `suspension` and `rackMounts` (sub-project 11), which its reader does not know: a bike it re-saves to the bike list, and the plan's bike in a draft or a setup it saves; both apps then read Not sure, and every other field stays (pinned in `tests/e2e/launch.spec.ts`, `BK-DETAILS-OLD-PAGE`). Saved setups (guided Trip, part 2; review of PR 80, I1, and its fix round): every older page (these two, and the page live before this one) cuts `loadcheck:setups` to 20 on every setup write and drops `kind`, `forRoute`, `base` and `isDefault`, so the bag planner keeps at most 20 there, the rest in `loadcheck:setups-more:v1`, and those four fields also in `loadcheck:setup-marks:v1`. The page starts with `storedSetups()` and follows other tabs with `storedSetupsLocal()`, both reading the three as one list (a setup in both lists reads once, from the first), and every setup write goes through `store.set(SETUP_KEY, list)` (`storeSetups`). A write that adds a setup lays the lists out afresh (all in the first while there are 20 or fewer; past 20 the general setups first, then the trip setups in the list's order); a write that adds none moves none, so a delete on a full storage always frees room, and the first list may hold fewer than 20 until a setup is added. The three values are written in an order where stopping after any one of them loses no setup (a setup moving to the other list is written there before it leaves the one it is in), and the first write that fails stops the rest: the page then says the save did not reach storage, and what was stored stays readable (pinned in `qa/setup-kinds.cjs`, `tests/unit/contracts/handoff.test.ts` and `tests/e2e/launch.spec.ts`, `SET-LIMITS`). A known risk, for the owner to rule on (review of PR 80, m-2): a stale tab of an older page (frozen in the background, or back from the back/forward cache, whose `pageshow` does not read the setups again) that saves a setup adds the setups of the first list it never saw to the ones it holds and cuts the result to 20, so every setup it never saw past those 20 is lost from both lists, not just one: 13 in the review's probe, where it held 18 and the bag planner had added 12 trip setups and 3 general ones since (pinned with both old pages in `tests/e2e/launch.spec.ts`). Between two old tabs the same cut needed the other tab to delete setups first, as each kept at most 20; with this page past 20 it needs nothing. A bag-planner tab open at that moment names what went ("13 saved setups were removed in another tab: …", `noteSetupsGone`); a tab that was closed cannot, and nothing brings the setups back but an export. Not pinned: (6) its theme button writes only `loadcheck:theme`, which the new apps read only while neither has a newer choice of its own (`THEME-ONE` below), and it follows only the bag planner's button, never a choice in You; until it is closed it can show another theme than the two apps. Contract 3 says the apply removes every key, so it does not leave empty lists the old tab would adopt.

## Rules

- `core` never imports from `ui`, `data` or `store`.
- `core` has no hidden inputs: no clock, randomness or device time zone. `now`, zone data and seeds are arguments. Lint enforces this.
- Rule IDs live in `docs/rules.md`, one line per rule ending in its ID. A test title starts with its ID, for example `test('[W-ZERO] …')`. `tests/rules-in-force.txt` lists IDs in force; a `later: ID` line is listed but has no test yet, and the task that adds the test removes the `later:` mark.
- Pull requests use fixed seeds.
- `main` accepts changes only through pull requests with green `types-lint`, `unit-property`, `load-check-qa` and `browser` checks.
- Never print or quote lines 20–25 of Load Check's page (`public/tools/bags/index.html`) in any copy. Read it only from line 26 on (`Read` with `offset` 26, or narrow Grep patterns). `.gitattributes` marks it `-diff`, so `git diff` and `git show` print nothing for it. Never run `gh pr diff` on a pull request that holds the page; review with `git diff -- . ':(exclude)public/tools/bags/index.html'`, and for the page's own edits `git diff --text -U0 -- public/tools/bags/index.html`, whose hunks must not touch lines 20–25.
- No `tel:` link is ever the first tap (owner's iPhone check, 6 November 2026: the iPhone's home-screen app dials one at once). Every call goes through `CallButton` in `src/ui/call.tsx`, which asks first with the number and who it is (`AH-CALL-CONFIRM`); never write a `tel:` href anywhere else, in either app, and keep `<meta name="format-detection" content="telephone=no">` on every page.
- The bag rules are frozen: `qa/selection-fixtures.cjs` and `LC-FREEZE-01` may not change without the owner.
- Load Check's source is now this repository. The project folder's `index.html` is the archive; don't edit it.

## A task

One group of related rules, 1–2 hours of work. Each task lists its rule IDs, spec sections, files and commands.

1. A failing test that names the rule ID.
2. The smallest code that passes.
3. `npm run fast`.
4. A commit.

## Deploys

A merge never deploys. Only the owner approves a deployment, and only the owner runs `emergency`, `preview` and `rehearsal`. Agents never start, approve or re-run any of these, never run `wrangler deploy`, `wrangler rollback` or `wrangler versions upload`, and never call GitHub's approval API.

After green checks on `main`, `deploy.yml`'s `decide` compares the build with the live `build.json`. Only a real difference asks for the owner's click on the `production-approval` environment; `deployEnabled` in `build.config.json` must be true before anything is even compared. `deploy.yml`'s `deploy` job, after that click, is the only ordinary way to `wrangler deploy` to `load-check`. A failed after-deploy check opens one issue labelled `after-deploy`; nothing rolls back by itself. `tools/env-production.json` and `tools/env-approval.json` hold the two environments' settings.

`decide` refuses to ask for a click, and fails, when `production-approval` has no required reviewer or can't be read, unless `deployWithoutReviewer` in `build.config.json` is true. Setting that to true is the owner's decision. `emergency`'s `check` action changes nothing and says where a rollback would go; `switch` builds from the commit that is live, and only with `also_release_main` from `main`.

## Only with the owner

- Changing a golden file, a regression case, a committed schema or a threshold.
- Skipping or loosening a test.
- Making anything public that was not public before.
